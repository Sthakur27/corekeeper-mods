# Inventory, UI, cosmetic and pet performance audit

Date: 2026-10-14. Read-only review of the current working-tree sources, including concurrent uncommitted work. No mod code, installation, settings, saves, publishing or running game was changed. Source paths and lines below are repository-relative and refer to this snapshot. These are ranked measurement hypotheses, not measured causes of lag. No runtime profiling was performed.

## Priorities

1. **Armor Dye: recurring diagnostic-string allocations and texture readback/cache churn.** Highest-priority measurement in this group. The string construction is directly visible; its frame-time impact is unmeasured.
2. **Loadout Fallback / Five Loadouts / Ender Stash: repeated player queries and writable buffer access.** Individually small player populations may make these cheap, but synchronous ECS access can cost more than the loop body. Measure together and by world.
3. **Stim Hits: projectile-history retention and exception floods under combat.** Event-driven sound processing is bounded by playback throttling, but bookkeeping has a different bound.
4. **Pet Editor / Mod Options: menu-open churn.** Expected to be localized to opening or displaying menus; low suspicion for general movement lag with menus closed.
5. **Master Pet Plus: legacy only.** Excluded from overhaul; do not republish. Inspect installed state before attributing any runtime cost to it.

No `DisableBurst` call was found in these eight mods. Master Pet Plus explicitly runs its own RPC job without Burst, rather than disabling a vanilla system. `Allocator.Temp` arrays below are native temporary allocations, not automatically managed GC allocations. Direct EntityManager access and synchronous query materialization are synchronization risks; this review does not establish their actual blocking time.

## LoadoutSharing / Loadout Fallback

- **Triggers/scans:** `LoadoutSharing/Scripts/LoadoutSharingMod.cs:40` calls handler sync, all-player vanity sync and vanity UI update every client frame. `Vanity/VanitySync.cs:24` loops `Manager.main.allPlayers` and reads active preset data. `HandlerSync.cs:89` checks ten local equipment kinds. `Patches/UIPatches.cs:7` adds work to every inventory-slot UpdateSlot, with a type filter before inherited-slot checks.
- **Simulation:** `Systems/LoadoutLayoutSystem.cs:33` queries every player each simulation update in both worlds, obtains writable contained/preset buffers and checks each preset; writes only changed layouts. `Systems/LoadoutPresetSyncSystem.cs:40` queries players in both worlds and synchronizes bag/pet references, queuing ClaimInventory only when changed. `Vanity/VanityPresetSystem.cs:30` copies three native arrays per update and writes changed vanity indices. This happens while walking with inventory closed.
- **Allocations/synchronization:** Native arrays are disposed; most hot-path work is bounded value processing. `_seen` in `LoadoutPresetSyncSystem.cs:22,53` retains each observed Entity for the world's lifetime, with no removal shown. UI construction allocates clones/textures once (`Vanity/VanitySlotsUI.cs:69,186`). Writable ECS buffer retrieval may wait for competing jobs despite unchanged values. No explicit Burst disabling or CompleteDependency call found.
- **Default/disabled:** Always active, no settings (`LoadoutSharingMod.cs:11`). This is a persistent slot-layout feature: do not remove it from an existing character as an ordinary A/B test.
- **Measure:** Each of the three OnUpdate methods, HandlerSync.SyncToEffective, VanitySync.SyncAll; world label, players checked, presets checked/changed, claims queued, query/materialization time versus loop time. Compare idle and rapid switching with 1 and several players, inventory closed/open, bag/pet fallback changes.
- **Mitigation hypothesis:** Move migration to player-ready lifecycle and invalidate effective slots after inventory/preset changes. Verify remote replication and all vanilla mutation paths before replacing consistency checks; missing events could cause item or equipment bugs. Cache UI context once per update rather than per equipment slot if measurements justify it.

## FiveLoadouts

- **Triggers/scans:** `FiveLoadouts/Scripts/Systems/PresetMigrationSystem.cs:36` scans all players every update in client and server worlds although buffer growth and preset append are normally one-time migration. `FiveLoadoutsMod.cs:46` calls PresetTabsUI.EnsureExtended every frame; `PresetTabsUI.cs:53` re-applies layout after tabs exist (bounded tab work).
- **Allocations/synchronization:** Migration makes/disposes a native entity array, obtains writable buffers, and only appends when short. UI clone/list/texture work occurs during initial extension (`PresetTabsUI.cs:64,74,114`); numeral extraction can use GPU ReadPixels (`PresetTabsUI.cs:565`). That is a first-use hitch candidate, not evidence of continuous readback. No Burst disabling or explicit job completion found.
- **Default/disabled:** Always active; five presets and persisted slots. No safe ordinary removal A/B on a valuable character.
- **Measure:** PresetMigrationSystem.OnUpdate, PresetTabsUI.EnsureExtended and initial numeral build separately; players visited versus migrated, number of layout rewrites. Join old/new character, reconnect to world, first inventory opening, repeated loadout swaps.
- **Mitigation hypothesis:** Process migration once per fully initialized player with a verified rejoin/reset path; drive tab extension/layout from window creation and layout events. Do not infer readiness from a single early observation.

## EnderStash

- **Triggers/scans:** `EnderStash/Scripts/Systems/StashGrowSystem.cs:27` copies player entities and PlayerGhost data every server update and calls StashGuard.Relocate. The normal established-layout path is small and returns at `StashGuard.cs:123`; missing/conflicting marker scans the whole contained buffer at `:124`. An occupied marker slot can cause this fallback on subsequent ticks until resolved. `Systems/EnderChestMerchantSystem.cs:40` scans all matching merchants, including prefabs and disabled entities, every two seconds, then scans fishing-merchant stock. This is explicit interval polling.
- **UI/events:** `EnderStashUI.cs:58` returns immediately when closed. Open/close, sort and quick-stack patches are event-triggered (`Patches/StashPatches.cs:8,20,30,45`). Sorting allocates snapshot arrays and lists (`EnderStashUI.cs:101,104,115`); quick-stack creates a HashSet at `:142`. Save relocation arrays allocate only on actual layout changes (`StashGuard.cs:68`).
- **Synchronization:** Native query copies and writable buffer access are the steady-state risk; no Burst disabling or explicit CompleteDependency found. Layout growth can reallocate dynamic-buffer storage. Do not confuse this with a per-frame managed array allocation.
- **Default/disabled:** Always active, no settings (`EnderStashMod.cs:11`); persisted inventory slots make removal unsafe as a routine comparison.
- **Measure:** StashGrowSystem.OnUpdate, both StashGuard.Relocate overloads, EnderChestMerchantSystem.OnUpdate, sort/quick-stack; track players, marker fast-path/fallback count, migrations, merchants examined/changed, queued swaps. Test steady idle, merchant spawn/load, full stash sort, character/world joins on disposable backed-up saves, including occupied-marker edge case.
- **Mitigation hypothesis:** Merchant registration on authoring/spawn plus one-time saved-world repair; player-ready migration plus explicit pending relocation processing. Preserve both character-save and world-save restore paths, and record repeated unresolved marker states without flooding logs.

## ArmorDye

- **Triggers/scans:** `ArmorDye/Scripts/ArmorRecolor.cs:15,35` runs after every player's ManagedLateUpdate. It reads three armor and active held layers, updates a player lookup, and checks material properties. `:54` walks active preview objects every IMod.Update. `:230` hooks every inventory-slot update. `ProjectileRecolor.cs:16,57` checks ownership on entity spawn; dyed projectiles cache child-component arrays at `:124` then scan their sprite/skin arrays every LateUpdate at `:138`. No world-wide entity query.
- **Concrete allocation issue:** Local-player `Probe` calls at `ArmorRecolor.cs:42,116` build a concatenated key and a detailed interpolated diagnostic string at `:167-168` before `LogOnce` tests the HashSet at `:173`. Thus logging once does not make string construction once. Active previews similarly construct log strings at `:69`. This happens without requiring a newly dyed item.
- **Cold-path GPU/memory risk:** `DyeTextures.cs:31` caches sheets, but clears all sheets once count exceeds 96 at `:35`; a diverse visible set could churn. A miss uses Graphics.Blit and synchronous ReadPixels (`:137-158`), creates textures and managed pixel arrays. Icon/sprite/source-pixel caches (`:12-20,48,60,94`) have no comparable eviction/cleanup in this file. `ArmorDyeMod.cs:57` has empty Shutdown. These are retained-memory and first-use-hitch hypotheses requiring counts and long-session tests. Material getters may also instantiate per-renderer materials; measure native memory/draw behavior rather than assuming managed timing explains it.
- **Default/disabled:** Held items, projectiles and icons default on (`DyeSettings.cs:20-22`). Their off settings are narrower than disabling the whole feature: armor hooks/Probe remain; existing projectile components restore vanilla and disable themselves at `ProjectileRecolor.cs:151`. Overhaul feature switches require restart to omit hooks. No broad Burst disabling or explicit dependency completion found; item auxiliary-data reads may synchronize ECS access.
- **Measure:** ArmorRecolor.Postfix/Probe/TickPreviews, SlotIconPatch.Postfix, ProjectileSpawnPatch.Postfix, DyedProjectile.LateUpdate, DyeTextures.Read/Sheet/Icon. Count probe calls, cache hit/miss, pixels read/recolored, sheets cleared, retained cache sizes, projectiles/layers visited. Compare undyed walking, cold first dye/palette opening, warm repeated palette opening, dense projectile combat, multiple dyed players, many successive colors.
- **Mitigation hypothesis:** Check diagnostic enablement/identity before building messages; use equipment/skin-change notifications where available. Cache or budget texture work, bound retained caches with safe reference ownership, and avoid whole-cache invalidation while visible renderers still need those sheets. Animation-driven sprite changes may still need a narrowly scoped render hook; do not replace necessary render updates with a blind timer.

## StimHits

- **Triggers/scans:** Damage effects, take-damage, death and audio-play Harmony hooks (`StimHits/Scripts/Patches.cs:130,164,220,249`). Most unrelated effects only pass a switch. `StimHitsMod.cs:85` also polls local attack input every frame and finishes pending audio loads. `SoundBank.cs:191` returns immediately with no request. Discovery is once at startup (`:85`) and selection preloads on OnChanged (`StimHitsMod.cs:75-78`). No whole-world scans.
- **Allocations/retention:** `Patches.cs:118` pruning allocates a map array and two lists. It runs only when RecentTargets.Count exceeds 256 (`:109`), while HitProjectiles accumulates unique projectile entities independently (`:102`). Repeatedly firing at a small set of targets can grow projectile history without that prune trigger. Measure both sizes; do not call the target threshold a bound on both maps. Exceptions are logged on every occurrence (`:156-159`, `StimHitsMod.cs:89`), a failure-path flood risk.
- **Bounds/defaults:** Playback is limited by 45 ms per-kind gap and an eight-source pool (`SoundBank.cs:30-31,224`). All sounds default Auto; object dings default false (`StimHitsMod.cs:62-72`). Turning all sounds Off skips playback/event work but still tracks input every frame and existing audio load work may finish. No Burst disabling or explicit completion found; ECS component reads can synchronize.
- **Measure:** Hits.TrackAttackInput/OnDamageNumber/Prune, SoundBank.Play/Update, total effect hook calls versus accepted hits, voice starts/throttles, map sizes, exception count. Sustained bow fire against one dummy, dense combat, all-Off comparison, large custom clip load, world rejoin.
- **Mitigation hypothesis:** Bound/prune each history map independently using event-driven admission/expiry; avoid input tracking when object dings are disabled; use input callbacks if native API exposes the needed semantics; throttle repeated diagnostics. Keep async-load completion checks bounded and lifecycle-driven.

## ModOptions

- **Triggers/scans:** `ModOptions/Scripts/ModOptionsMod.cs:24` calls SettingsMenu.Update every frame; `UI/SettingsMenu.cs:38` performs existence checks and only builds/injects missing menus. Discovery runs on OpenList (`:55-62`), not while walking. `ConfigDiscovery.cs:23,47` snapshots mods and groups/config-sorts entries on that action.
- **Allocations/defaults:** Opening list/page destroys prior row objects and clones replacements (`SettingsMenu.cs:229,240`), with lists, delegates, LINQ and regex strings in discovery. Setting rows only add timeout checks to their normal Update (`SettingsRow.cs:75`); not a per-frame full rediscovery. Library is always available; closed menus retain only the small bootstrap check. Failure disables retry at `SettingsMenu.cs:50` rather than repeatedly logging.
- **Synchronization/Burst:** No ECS world scan, explicit completion or Burst disabling found. Native object creation and text layout can still make menu-open frames expensive.
- **Measure:** SettingsMenu.OpenList/OpenPage/Rebuild, ConfigDiscovery.Scan, initial BuildMenus; entries inspected, accepted settings, rows created/destroyed, opening-frame duration, retained objects after repeated navigation. Test few versus many installed configs and repeated menu back/open cycles.
- **Mitigation hypothesis:** Reuse menu rows and cache discovery with explicit invalidation if measurements show meaningful opening hitches. Preserve live settings references and validation; avoid adding background config scans to make menus faster.

## PetEditor

- **Triggers/scans:** `PetEditor/Scripts/PetEditorMod.cs:42` calls UI.Tick every frame, but `PetEditorUI.cs:54-58` exits unless built and showing. Visible rows reread the equipped pet and construct level/color strings (`:151-165`). Native UpdateTalents hook (`PetEditorPatches.cs:12`) scans talent slots/picker entries (`PetEditorUI.cs:103-126`), including visibility checks for picker entries even when picker closed.
- **Allocations/defaults:** UI clones/buttons/picker creation allocate at build (`PetEditorUI.cs:241,268,347`); visible-frame labels allocate interpolated strings even if text is unchanged. No feature-level settings in standalone. Server edits are command-driven (`PetCommand.cs:14`, `PetServer.cs:15,52,74,86`), touching the equipped pet and its short talent buffer. No world scans, explicit job completion or Burst disabling found; direct ECS edits can synchronize during commands.
- **Measure:** PetEditorUI.Tick/UpdateRows/AfterUpdateTalents, first Build/picker build, PetServer setters; visible versus hidden calls, picker entries updated, actual pet state changes. Compare walking with editor closed, idle open tree, open picker, repeated level/color/talent edits on host and remote client.
- **Mitigation hypothesis:** Update row strings only on state change, picker contents on open/pet-state change; prefer native pet-window lifecycle notifications over the small closed-window poll where reliable. Preserve replication-driven refreshes after server command completion.

## MasterPetPlus (legacy/excluded)

- **Triggers/scans:** `MasterPetPlus/Scripts/MasterPetMod.cs:80` checks UI state every frame; GameObject.Find at `:96` repeats while the pet window reference is missing. `UI/MasterPetUI.cs:83` checks equipped pet while its object is active and refreshes on object/aux-index changes. UI interaction/mouse patches run from native UI events (`Patches/MasterPetUIPatches.cs:8` onward).
- **Allocations/sync:** UI refresh makes material/gradient/textures (`MasterPetUI.cs:238,305,341`) and talent-refresh arrays (`:410`); most are refresh/build paths. `Systems/SetPetTalentIDSystem.cs:14` requires RPCs, and `:75-76` runs its own job WithoutBurst synchronously. Generated implementation explicitly calls CompleteDependency only with a nonempty RPC query (`Generated/SetPetTalentIDSystem__System_19995521690.g.cs:187-191`). This is event-driven RPC work, not the Golden Chance pattern of deoptimizing vanilla inventory every tick.
- **Default/disabled:** Legacy installed standalone only if actually present; excluded from overhaul. Closed custom UI avoids its MonoBehaviour Update, but the mod's injection/reference checks remain. No global settings-off path identified.
- **Measure if installed:** MasterPetMod.Update missing-window retries, MasterPetUI refresh methods, SetPetTalentIDSystem.OnUpdate with RPC count and dependency-wait attribution; first UI opening, repeated talent changes, world transitions. Prefer clean-room Pet Editor for current maintenance. No changes or republishing of this fork are proposed.

## MasterPet_original_bundles

Directory inventory contains only Linux/Windows `.assetbundle` files and their `.manifest` companions. It is an asset archive, not an independently loaded source mod in this audit (no ModManifest.json/scripts found). No separate CPU update loop can be attributed to this folder; loaded behavior belongs to the consuming mod. Keep it excluded from commits and releases.

## Measurement safeguards

- Keep frame-time comparisons alongside method timings: synchronous waits, GPU readback, allocations and native material/texture costs can escape a narrow loop timer.
- Record client/server world separately; single player hosts both, so do not collapse two invocation streams into an unexplained call count.
- Count examined versus changed entities and cold versus warm cache misses. Separate initial loading/menu creation from steady walking.
- Do not disable slot-layout mods on the user's real saves. Use isolated copied characters/worlds and preserve installed layout during normal profiling.
- These recommendations require measured baselines and event-coverage verification before broad rewrites. This audit deliberately made no gameplay-code changes.
