# Simulation mod performance audit

Reviewed 2026-10-14; working-tree source, HEAD observed as `03e8e42`. Static inspection only: no game measurements, installation, publishing, or gameplay changes. Source references are repository-relative with one-based physical line numbers. Generated source uses `#line`; its references below mean physical file lines.

## What to measure first

1. **Faster Mushrooms:** recurring broad scans even at 1x, plus batches of environment respawn requests. Measure steady state and the frames after each respawn separately.
2. **Auto Replant:** each pending harvest can enumerate every dropped item repeatedly. Measure large area harvests with many unrelated ground items and missing seeds.
3. **Fast Auto Fishing:** generated component access explicitly completes dependencies before checking whether auto-fishing is disabled. Measure the pre-check portion while not fishing, not just catches.
4. **Keep Minions / Infinite Ore Boulders:** recurring entity snapshots and main-thread reads even when nothing changes. Measure cost versus entity population.
5. **Vehicle Speed / Bigger Watering Cans:** repeated discovery scans after initial application. Likely narrower workloads, but good candidates for removing unnecessary work after measurement.

These are investigation priorities, **not measured severity rankings or proven causes of lag**. None of the eleven reviewed mods contains a Burst-disabling call. Managed ECS access can still wait for conflicting jobs; timings must distinguish work from dependency waits. `Allocator.Temp` snapshots allocate native temporary memory, not automatically managed garbage. Managed lists, dictionaries, strings, and arrays are called out separately.

All eleven appear in `Overhaul/Scripts/Features.cs:32`. `release/build_overhaul.py:106` injects a restart-frozen feature guard into standard `OnUpdate` overrides, disabling the system on its first update; `OnCreate` is not gated. This is distinct from an in-feature setting such as 1x or Off. Fast Auto Fishing has an additional generated-method caveat below. Verify the built artifact when testing switches; standalone source lacks overhaul guards.

## Auto Replant

- **Trigger and frequency:** server simulation every update while the database exists (`AutoReplant/Scripts/Systems/AutoReplantSystem.cs:127`). Harvest detection queries enabled destruction and player-kill markers, rather than scanning every crop (`:108`). Actual replant attempts run for pending harvests until their six-second deadline (`:54`, `:192`). Seed mapping scans the database once (`:401`).
- **Work and allocation:** `TakeDroppedSeed` snapshots and scans the entire dropped-item query separately for each pending replant (`:249`, `:252`), before applying its distance filter. With H pending harvests and D drops this can approach H×D inspections per update; repeated retries multiply that further. `CountSeeds` and `FindSeedSlot` scan inventory buffers (`:347`, `:380`). `PruneSeen` allocates a new managed stale-claim list whenever claims exist (`:440`). Taking the last ground seed calls direct `EntityManager.DestroyEntity` (`:278`), a structural-change/synchronization candidate. Seed creation uses a command buffer (`:291`), and inventory consumption uses the native change queue (`:234`).
- **Defaults and disabled:** enabled and inventory seeds on by default; golden override off (`AutoReplant/Scripts/AutoReplantMod.cs:23`, `:73`). Disabled clears pending work but still calls `PruneSeen` every update (`AutoReplant/Scripts/Systems/AutoReplantSystem.cs:131`). `_now` updates only on the enabled path (`:140`), so claim expiry can stop advancing while disabled: bounded historical state may continue to be scanned/allocate the stale list until re-enabled. This is a static lifecycle observation, not a measured leak rate.
- **Mitigations:** harvest markers, duplicate suppression, six-second expiry, cached seed map, reusable seen scratch list, queued inventory edits. No Burst removal.
- **Instrumentation:** `OnUpdate`, `DetectHarvests`, `ProcessPending`, `TakeDroppedSeed`, `PruneSeen`. Counters: harvested/pending/expired, dropped candidates inspected, ground-seed hits, inventory slots examined, immediate destroys, claims. Compare empty ground versus accumulated loot, single harvest versus hoe area harvest, with/without seeds. If confirmed, snapshot/index drops once per update and reuse a stale-claim list; investigate a native pickup/drop association before any broad inventory interception.

## Faster Mushrooms

- **Trigger and frequency:** growth system runs every simulation update when root plants exist (`FasterMushrooms/Scripts/Systems/FasterMushroomsSystem.cs:71`, `:74`). It processes roots including disabled entities (`:58`), all flora growers (`:63`), and all growth timers with grower references (`:64`), then filters for mushrooms in managed loops. Positive mushroom classification still reads component data (`:190`).
- **Work and allocation:** three snapshots for roots (`:92`), two for growers (`:138`), three for stage timers (`:163`): up to eight native temporary arrays per update. Cache clearing every 601 updates (`:79`) can cause a recurring classification burst. Component reads/writes may wait on jobs; writes are guarded by comparisons.
- **Respawn path:** `MushroomRespawnSystem.OnUpdate` starts with a ten-second delay, then defaults to once per minute (`FasterMushrooms/Scripts/Systems/MushroomRespawnSystem.cs:35`, `:60`; `FasterMushrooms/Scripts/MushroomSpeed.cs:86`). `CollectAreas` builds a managed HashSet and player-transform snapshot (`MushroomRespawnSystem.cs:104`). Radius 48 with inclusive 16-tile area bounds gives 7×7 = 49 areas per player before overlap deduplication (`:113`). All requests are created using direct `EntityManager.CreateEntity` in one update (`:95`). The expensive vanilla spawning work can occur later; timing only this mod misses it. The environment table is temporarily edited (`:80`) and restored once requests drain or after 30 pending updates (`:53`).
- **Defaults and disabled:** growth defaults to 4x (`MushroomSpeed.cs:20`). **1x still performs all three scans**; it is not a performance-off setting. Respawn Off returns early except for restoration of an already-pending batch (`MushroomRespawnSystem.cs:53`). Full overhaul feature off on restart is the isolation test.
- **Mitigations:** mushroom ID cache, write-only-on-change, overlap deduplication, waits for existing respawn requests, restoration timeout. No Burst removal.
- **Instrumentation:** the three growth pass methods individually; `CollectAreas`, respawn enqueue and restore; counters for each query population, matched mushrooms, writes, queued areas, pending lifetime. Correlate following frame times with request counts. Test ordinary area versus large farm, 1x versus full feature off, and respawn Off versus 1 min. Consider conversion/settings-driven baseline edits, newly-created entity handling, and bounded request batches only after confirming native rules and restoration correctness.

## Fast Auto Fishing

- **Trigger and frequency:** `fastfish_sys.OnUpdate` runs in both client/server PlayerStateSystemGroup (`FastAutoFishing/Scripts/fastfish.cs:21`), taking a player snapshot each update (`:57`) and checking four timers for every entity with PlayerGhost/FishingStateCD. It does not query only actively fishing players. `spoof_sys` runs client-side after input sending (`FastAutoFishing/Scripts/spoof.cs:24`) and checks the singleton local player. Button `LateUpdate` reads singleton state every UI update (`FastAutoFishing/Scripts/switch.cs:41`).
- **Synchronization:** generated `__OnUpdate_450AADF4` uses `GetComponentRWAfterCompletingDependency<ClientInputData>` and read variants for equipment and fishing state (`FastAutoFishing/Scripts/Generated/spoof__System_12394320590.g.cs:40`, `:47`, `:49`). The disabled check is **after** these calls (`:52`). That is explicit dependency-completion behavior, but actual waiting time is unmeasured. Timer squash uses direct component access and writes only changed timers (`fastfish.cs:71`).
- **Defaults and disabled:** new state defaults auto-fishing on (`spoof.cs:38`). Toggling auto off stops input mutation after reads, but does **not** disable `fastfish_sys`, so accelerated fishing timers remain active. Saves serialize JSON on creation when initializing defaults and on destruction (`spoof.cs:41`, `:119`; `state.cs:22`), not every frame.
- **Overhaul caveat:** the builder guards standard `OnUpdate`, but the compiler-generated replacement method is named `__OnUpdate_450AADF4`. Its body does not match that guard pattern. Verify loader-generated dispatch and the built source before assuming full feature off suppresses spoof work. This is an isolation-test correctness risk, not confirmation that the guard is bypassed at runtime.
- **Mitigations:** player-sized workload, RequireForUpdate, timer writes only on change, no Burst removal, existing generated code supplied for SystemAPI access.
- **Instrumentation:** `fastfish_sys.OnUpdate`, actual generated spoof update (avoid double-counting wrapper/replacement), button `LateUpdate`; counts of inspected players, timers changed, auto-off calls, rod-off calls, catches. Compare disabled auto, non-fishing, active fishing, and full mod exclusion in a test install. Evaluate moving cheap enable/slot checks before writable input access while preserving dependency safety. Faster catches also increase vanilla inventory/loot/XP workload: compare total frame time, not only custom code.

## Better Fishing Loot

- **Trigger and frequency:** both worlds read the loot bank each update, but only call `FishingLootPatcher.Apply` when settings version or bank identity changes (`BetterFishingLoot/Scripts/Systems/FishingLootWeightSystem.cs:28`).
- **Work and allocation:** Apply scans all table headers and entries of matching fishing tables (`BetterFishingLoot/Scripts/FishingLootPatcher.cs:66`, `:74`, `:83`). Stores original weights, caches table classification, looks up object info for rarity. Logging creates a StringBuilder and lists only when multiplier changes (`:69`, `:81`). Dictionary key overrides object equality (`:33`); measure allocation if repeatedly reapplying rather than assuming no boxing. Blob edits use the native loot pathway without per-catch custom rolls or Burst removal.
- **Defaults and disabled:** default 5x (`BetterFishingLoot/Scripts/FishingLootConfig.cs:15`); 1x restores weights through the same version-triggered apply and then returns to cheap singleton/hash/version checks. Full feature off requires restart in overhaul.
- **Instrumentation:** cheap-path `OnUpdate` separately from `Apply`; count table headers, entries, modified entries, apply calls and bytes allocated. Test startup and repeated settings changes. Low steady-state risk from source structure; no runtime cost established. Bank readiness could eventually use a lifecycle event, but do not trade a cheap identity check for a fragile patch.

## Bigger Watering Cans

- **Trigger and frequency:** authoring event and factory postfix change sizes during conversion (`BiggerWateringCans/Scripts/BiggerWateringCansMod.cs:43`; `BiggerWateringCans/Scripts/Patches/ObjectAuthoringPatch.cs:10`). A both-world system fixes the database once, then snapshots all players with the placement-size buffer every update (`BiggerWateringCans/Scripts/Systems/WateringCanSizeSystem.cs:35`, `:44`).
- **Work and allocation:** one native entity array per update even after all players were reset. HashSet suppresses repeated writes (`:48`) but does not suppress scanning; the set retains historical player entity identities for the world's lifetime. Buffer access is only for newly seen players. No explicit dependency completion or Burst disabling.
- **Defaults and disabled:** no standalone toggle; 2×2/4×4 fixed sizes (`BiggerWateringCans/Scripts/CanSizes.cs:14`). Full overhaul feature off skips authoring registration/patch and system work after restart.
- **Instrumentation:** `WateringCanSizeSystem.OnUpdate` / `FixBlob`, players inspected versus newly reset, set count, authoring calls. Test join/rejoin, unchanged idle world, and watering. Native watering now touches more tiles per action; record action frame costs too. A reliable player-created callback could eliminate the recurring reset-discovery scan.

## Buff Duration Floor

- **Trigger and frequency:** both-world `ConsumableDurationFloorSystem.OnUpdate` calculates prefab count every update, and only does full work when count/settings version change (`BuffDurationFloor/Scripts/Systems/ConsumableDurationFloorSystem.cs:61`).
- **Work and allocation:** full pass snapshots consumable prefabs, allocates two managed HashSets, and caches original duration arrays per prefab (`:71`, `:74`, `:82`). Condition fallback converts enums to strings (`BuffDurationFloor/Scripts/ConditionFilter.cs:46`) on apply, not continuously per buff. Buffer access can synchronize with readers. No Burst removal.
- **Defaults and disabled:** buff floor 180s, healing Off (`BuffDurationFloor/Scripts/FloorSettings.cs:22`). Both Off still perform the count/version check; one apply restores original values. Requiring `Prefab` explicitly (`ConsumableDurationFloorSystem.cs:48`) is an important existing mitigation: dropped/streamed live items cannot cause full rescans by changing this query count.
- **Instrumentation:** cheap-path count and full apply separately; prefabs/entries visited, writes, apply calls. Validate idle, world load, settings edits, and many dropped consumables. Retain current caching unless measurement justifies replacing the count check with a reliable lifecycle notification.

## Boss Bonus Loot

- **Trigger and frequency:** server death-processing query every update (`BossBonusLoot/Scripts/Systems/BossBonusLootSystem.cs:78`), enabled EntityDestroyedCD restricts matches to destruction phase (`:69`). Query covers ordinary dying creatures too because the bonus table includes Mimites, turrets, and Void Larvae. A separate both-world Hydra bank system only rewrites on bank identity change (`BossBonusLoot/Scripts/Systems/HydraGemSystem.cs:54`).
- **Work and allocation:** death system snapshots four arrays (`BossBonusLootSystem.cs:89`), filters IDs, tracks handled entities, prunes that set every update (`:80`), spawns bonus stacks using native `DropNewEntity` (`:109`), and **logs each eligible death** (`:114`). Dense farms of eligible non-boss enemies could make logging/extra drops more relevant than boss fights. Hydra path builds log lists and strings only on bank application (`HydraGemSystem.cs:61`). No Burst removal; entity reads and native drop creation warrant synchronization measurement.
- **Defaults and disabled:** no settings; always on unless excluded or overhaul switch off on restart. Duplicate suppression and empty-query return mitigate repeated death processing.
- **Instrumentation:** `BossBonusLootSystem.OnUpdate`, `HydraGemSystem.OnUpdate`; dying candidates, handled-set size, eligible deaths, actual bonus stacks, logs/sec. Test mass eligible deaths versus ordinary combat, observe subsequent pickup/render costs. Aggregate death logging if measured logging volume warrants it.

## Infinite Ore Boulders

- **Trigger and frequency:** every server health-system update before native health application (`InfiniteOreBoulders/Scripts/Systems/InfiniteOreBouldersSystem.cs:20`, `:49`). Query matches all objects with drop-on-damage and health, then checks cached ore-boulder ID classification (`:31`, `:38`).
- **Work and allocation:** three native snapshots each update (`:51`), health read for all candidates, boulder health restored only when changed, damage-buffer loop for every boulder having that buffer (`:66`). Buffer access and health writes can wait on jobs even if many buffers are empty. No Burst removal.
- **Defaults and disabled:** always on, no standalone setting. Full overhaul feature off after restart suppresses update. Cached enum classification and guarded health writes are existing mitigations.
- **Instrumentation:** `OnUpdate`; candidates/boulders, nonempty damage buffers, damage entries, health writes. Compare idle loaded boulders against active multi-drill farms and many drop-on-damage non-boulders. Explore processing pending damage rather than all boulders, but preserve pre-damage refill and lethal-damage protection ordering.

## Keep Minions

- **Trigger and frequency:** three server run-group updates bracket MinionHandlerSystem (`KeepMinions/Scripts/Systems/KeepMinionsSystems.cs:18`, `:64`, `:92`). Hide snapshots players with enabled DisablePhysicsCD, then tests teleport/alive state (`:30`, `:45`). Restore visits only hidden players (`:75`). Bring scans every live minion every update (`:117`) to detect distance >32 tiles.
- **Work and allocation:** three native snapshots for Hide (`:45`), three for Bring (`:119`), even when loops are empty; direct enable-state changes and owner/transform reads around native minion processing may introduce waits. Hidden list is reused. The ordering intentionally preserves native behavior except for minion destruction during teleport. No Burst removal.
- **Defaults and disabled:** no standalone setting. Full overhaul feature off after restart gates all three systems. Teleport checks do not eliminate the continuously running minion-distance scan.
- **Instrumentation:** each of the three `OnUpdate` methods separately; disabled-physics candidates, hidden/restored counts, minions visited, owners read, minions moved. Test zero minions, maximum practical minions, multiple owners, teleport and idle combat. Investigate teleport landing events for repositioning; keep correctness of the pre/post flag bracket if native events cannot replace it safely.

## Vehicle Speed

- **Trigger and frequency:** both-world timer every 0.5s, or immediately on settings version change (`VehicleSpeed/Scripts/Systems/VehicleSpeedSystem.cs:22`, `:48`). Requires some boats/karts, but scans all matching live vehicles on each pass.
- **Work and allocation:** two native snapshots (`:59`, `:73`), component reads for each vehicle; writes only changed multipliers. Prefab baselines are cached by ObjectID (`:55`). If a prefab class never appears, its empty cache causes repeat `ReadPrefabs` calls (`:87`). Managed log lists are built only after a successful baseline read.
- **Defaults and disabled:** both speeds default 1x (`VehicleSpeed/Scripts/SpeedSettings.cs:9`), but scans still run at 1x. Full overhaul off requires restart. No Burst removal.
- **Instrumentation:** `OnUpdate` and `ReadPrefabs`; vehicle counts, changed counts, baseline reload attempts, total time per world. Test one versus many parked vehicles and 1x versus full feature off. Candidate redesign: native creation/conversion values plus explicit settings-change application, with saved-entity migration once; verify both prediction worlds before replacing polling.

## Durability Multiplier

- **Trigger and frequency:** both worlds before native ChangeDurabilitySystem in EndPredictedSimulationSystemGroup (`DurabilityMultiplier/Scripts/Systems/ScaleDurabilityLossSystem.cs:24`). Queries target enabled durability-loss triggers plus Simulate (`:37`). The implementation changes native requests, not every inventory item.
- **Work and allocation:** for rate below 1x, two native entity snapshots (`:53`, `:70`), trigger and replicated RNG reads/writes. These may synchronize with preceding producer jobs; no explicit Burst disable. Armor and held-loss requests are bounded by players/active triggers, not inventory size. Count actual calls during client prediction rather than assuming exactly one per rendered frame.
- **Defaults and disabled:** default 0.5x (`DurabilityMultiplier/Scripts/DurabilityRate.cs:14`). At 1x returns before arrays or RNG (`ScaleDurabilityLossSystem.cs:50`). At 0x it still processes triggers to cancel losses; zero loss is not feature off. Full overhaul off requires restart.
- **Instrumentation:** `OnUpdate`; held/armor trigger count, RNG calls, requests canceled/changed, calls per rendered frame and world. Compare idle versus continuous mining/combat and host versus joining client. This is a useful native-pathway example to preserve unless measurements identify a specific wait or allocation problem.

## Measurement rules for this group

- Label every sample by world and method. Predicted/run groups can execute more than once per rendered frame; do not infer cost from call count alone.
- Capture whole-frame distributions as well as method totals, especially after respawn requests, bonus drops, faster catches, and structural changes.
- Count native snapshot elements/bytes separately from managed GC allocations. Do not add logging inside entity/item loops to measure them.
- Compare default, explicit no-op setting, and restart-disabled feature as separate cases. They are not equivalent in these sources.
- Do not disable Burst or patch job internals to time them. If method timing cannot explain an A/B difference, use a profiler capable of observing dependency waits/native jobs in a controlled test session.
- Findings here authorize investigation, not broad gameplay refactors. Preserve multiplayer prediction, inventory ownership, and restore paths when optimizing.
